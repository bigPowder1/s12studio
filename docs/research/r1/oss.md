**Conclusion:** none of these accepts CodeWarrior's assembler dialect. The authoritative spec for that dialect is the NXP *HC12 Assembler Reference Manual* ([HC12ASMRM.pdf](https://www.nxp.com/docs/en/reference-manual/HC12ASMRM.pdf); mirror [CW_Assembler_HC12_RM](https://my.eng.utah.edu/~cs5780/doc/CW_Assembler_HC12_RM.pdf)). Its features include `ABSENTRY`, `XDEF/XREF/XREFB`, `SECTION`/`ORG`, `DC.B/W/L`, `DS`, `DCB`, `EQU/SET`, `MACRO/ENDM` with `\1`-style params, `IF/IFDEF/ELSE/ENDIF`, `INCLUDE`, `LIST/NOLIST`, `$` hex, `%` binary, `@` octal, `*` or `;` comments, labels with or without a colon, and expressions with `HIGH`/`LOW`/`PAGE`. Wrapping GAS would need a source-to-source translator that is about as much work as a real assembler, and error line numbers would map back to the original file poorly. **We should write our own TypeScript assembler for the CW dialect, and use GAS and libasm only as test oracles in CI.**

## 3. CodeWarrior .mcp project files

- **Format:** proprietary binary and undocumented. The best open prior art is **burgerbecky/makeprojects** `codewarrior.py::parse_mcp_file` (MIT, Rebecca Ann Heineman) [raw](https://raw.githubusercontent.com/burgerbecky/makeprojects/master/makeprojects/codewarrior.py), [docs](https://makeprojects.readthedocs.io/en/latest/doxygen/namespacemakeprojects_1_1codewarrior.html):
  - Magic in the first 4 bytes: `b"cool"` means big-endian, `b"looc"` means little-endian.
  - u32 at offset 16 is the index offset; the u32 at that location points to the string table.
  - u32 at offset 28 is the version (50 = CW 9 Win, 58 = CW 10 Mac, 59 = CW for Nintendo).
  - 19-byte project identifier at offset 40.
  - The string table holds NUL-terminated `"TargetName:PanelName"` strings, which give the target names (e.g. "Full Chip Simulation", "Serial Monitor"/"P&E Multilink") and settings panels.
  - **UNCERTAIN:** whether CW for HC12 v5.x (IDE 5.7/5.9) uses the same container or version number. It is very likely the same IDE family; we need real lab .mcp samples.
- An NXP forum user reports that source file names are visible as plain strings in the .mcp ("a lot of other goobledegook"). So a heuristic string scan for `*.asm/*.inc/*.prm` paths is a viable fallback for the file list. The NXP thread returned 403 to the fetcher; search snippet only. [thread](https://community.nxp.com/t5/Classic-Legacy-CodeWarrior/Code-Warrior-Project-File-Listing/td-p/153613)
- **Official escape hatch:** the IDE's File > Export Project writes `.xml`, and `cmdide.exe /x` imports XML. No headless export exists [NXP thread](https://community.nxp.com/t5/S12-MagniV-Microcontrollers/Script-wizard-to-convert-exported-mcp-xml-Project-to-makefile/m-p/131384). If the lab can export XML once, an **XML importer is much more reliable** than binary parsing. Support both.
- **Recommendation:** treat `.mcp` as read-mostly. Infer the project from the conventional CW wizard folder layout: `Sources/main.asm`, `Sources/derivative.inc` / `mc9s12dg256.inc`, `Prm/*.prm` (relocatable only), `cmd/*_Startup.cmd` etc., `*.ini` per debugger target (`Full_Chip_Simulation.ini`, `SofTec`/`P&E`/`Serial_Monitor.ini`), `bin/*.abs`, `*.abs.s19`, `C_Layout.hwl` (debugger window layout). That layout is from my knowledge and is **UNCERTAIN**; verify against a real lab project. Keep a JSON sidecar for our own settings and never rewrite the binary .mcp.
- Absolute-assembly projects (assembler output goes straight to .abs via `ABSENTRY`, no linker) are what assembly-only classes usually use. Relocatable-assembly projects need a linker that understands `.prm` (`SEGMENTS`/`PLACEMENT`/`VECTOR`/`INIT`). Both modes are described in HC12ASMRM and the CW linker manual.

## 4. File-format libraries (JS)

- **S-records:** `node-srec` (v0.1.5, about 12 downloads a week) [npm](https://npmjs.com/package/node-srec). "srec-parser" is cited only by low-quality tutorial sites and is unverified. **Write our own.** S0/S1/S2/S3/S5/S7/S8/S9 with checksums is about 150 lines of TS. Paged S2 records for banked flash (`PPAGE` linear vs. banked `0x308000`-style addresses) need care, because CW and D-Bug12 use different address conventions (**UNCERTAIN**; verify).
- **ELF/DWARF:** `elf-tools` (MIT, builds/parses ELF, last release 2020) [npm](https://www.npmjs.com/package/elf-tools). Kaitai Struct ELF parser for reading [kaitai](https://formats.kaitai.io/elf/javascript.html). **No JS DWARF writer exists.** CW's `.abs` is ELF/DWARF with HC12 machine type. We don't need to emit DWARF: our own debug map (address to file:line, symbols) in JSON is enough. Reading CW-produced `.abs` files is optional (nice to have for "open existing build").

## 5. Hardware connectivity prior art (Dragon12)

- **D-Bug12** (resident monitor on the Dragon12-Plus): the text protocol is documented in the *D-Bug12 Reference Guide* [DB12RG4](https://community.nxp.com/pwmxy87654/attachments/pwmxy87654/8bit/22031/1/DB12RG4.pdf). It covers `LOAD` of S19, `G`, `T` (trace), `BR`, `MD/MM`, `RD/RM`. A Python wrapper exists [pypi dbug12](https://pypi.org/project/dbug12/). It is not designed as a debugger back end, and it cannot program its own flash. It is good enough for "download & run + register/memory view + breakpoints" in RAM/EEPROM.
- **AN2548 Serial Monitor** (what CW's "HCS12 Serial Monitor" target talks to): a 2 KB monitor in flash, 23 binary primitive commands over SCI0, sends a long break after reset, and needs interrupts enabled for memory access and halt [AN2548.pdf](https://NXP.com/docs/en/application-note/AN2548.pdf). The source package (HCS12_SERIALMON.zip, CW-format asm) is no longer at an obvious NXP URL (**UNCERTAIN**). **hcs12mem** (C, GPL) implements the AN2548 host side and is a protocol reference [thread](https://www.embeddedrelated.com/showthread/68hc12/15482-1.php).
- **BDM:** USBDM (GPL-2.0, open hardware and host DLL, includes a GdbServer) [repo](https://github.com/podonoghue/usbdm-eclipse-makefiles-build). HCS12 support is from memory and **UNCERTAIN** in this check. P&E Multilink is proprietary; skip it.
- **Serial in Electron:** there are two options.
  - Chromium **Web Serial** in the renderer: `navigator.serial` plus `session.on('select-serial-port')`, `setDevicePermissionHandler`, and a blocklist override switch. It needs **no native module** [Electron devices](https://www.electronjs.org/docs/latest/tutorial/devices). Break-signal support (needed for AN2548 reset/attach) exists through `SerialPort.setSignals({break:true})` in Chromium (**UNCERTAIN** for long-break timing).
  - `serialport` npm (MIT, N-API prebuilt binaries "should work without issue" in Electron) [docs](https://serialport.io/docs/guide-installation).
  - Prefer `serialport` in the main process or a utility process if precise break or latency control is needed. Otherwise Web Serial avoids native rebuilds.

## 6. Editor / UI stack

- **Monaco Editor** (MIT):
  - Register the language with `monaco.languages.register` + `setMonarchTokensProvider`. Samples: [browser-amd-monarch sample in monaco-editor repo]. Cover CPU12 mnemonics, CW directives, `$`/`%`/`@` literals, `*` comments only at column 1, and `;` comments.
  - Breakpoints: `glyphMargin: true`, use `editor.createDecorationsCollection` (`deltaDecorations` is deprecated) with `glyphMarginClassName`, and `onMouseDown` with target type `GUTTER_GLYPH_MARGIN`. Ready-made option: `monaco-breakpoints` npm [npm](https://npmjs.com/package/monaco-breakpoints).
  - Current-PC line: whole-line decoration `isWholeLine` + `className`, plus `revealLineInCenterIfOutsideViewport`.
  - Vite/Electron: import workers with `?worker` and set `self.MonacoEnvironment.getWorker`. Only `editor.worker` is needed for a Monarch-only language. Use a relative `base` so workers resolve in packaged `file://` apps, and module workers for newer Monaco versions (0.53+; **UNCERTAIN** details) [waveterm PR](https://github.com/wavetermdev/waveterm/pull/2401/files). `@monaco-editor/react` loads from a CDN by default, so configure it for local loading in Electron. Alternatively, `vite-plugin-monaco-editor` [repo](https://github.com/vue3-oop/vite-plugin-monaco-editor).
  - Alternative: **CodeMirror 6** (MIT). Lighter, no workers, first-class gutter API. Reasonable if Monaco bundling becomes painful. CW's editor is plain, so we don't need Monaco's richness, but Monaco gives find/replace, multi-cursor, and minimap for free.
- **Disassembly / memory / register panes:** custom virtualized React grids (e.g. `react-window`), not Monaco. Hiwave's Memory window needs editable hex cells, address-format switching, and change highlighting.
- **xterm.js** (`@xterm/xterm`, MIT, used by VS Code; addons fit, webgl, search, serialize) [repo](https://github.com/xtermjs/xterm.js). Use it for SCI0/SCI1 terminal windows (simulated) and the D-Bug12 console (real board). The hiwave "Command" window can also be xterm-based or a simple input plus log.
- **Docking (MDI-like hiwave windows):**
  - **dockview** (MIT core; enterprise package proprietary; zero deps; React/Vue/Angular/vanilla; floating groups, **popout windows**, layout serialization; about 3.5k stars) [repo](https://github.com/mathuo/dockview). **Recommended.** Floating groups approximate hiwave's free-floating child windows. Serialized layouts can emulate `.hwl` layout files.
  - flexlayout-react (Caplin, MIT, popouts) is a good alternative. golden-layout v2 (MIT) is maintained more slowly. Maintenance status of both is from memory, **UNCERTAIN**.
  - The classic CW IDE (project window plus editor windows) is also MDI. True OS-level child windows are possible with multiple `BrowserWindow`s, but in-app floating panels are simpler and closer to the 2000s MDI look.
- **Scaffold:** **electron-vite** (MIT, v5.0.0, Node 20.19+/22.12+, Vite 5+, separate main/preload/renderer configs, HMR, `npm create @quick-start/electron@latest` with a `react-ts` template) [guide](https://electron-vite.org/guide/).

  - **Vitest** for the assembler, simulator, S19 and .mcp parser (pure TS, fast).

## 7. Recommendation: build vs. wrap

**Build our own assembler, linker and simulator in TypeScript.** Use GPL and native tools only as offline test oracles.

Reasons:
1. **Dialect:** no existing assembler accepts CodeWarrior HC12 syntax. Translation plus wrapping costs about as much as writing a dedicated two-pass assembler, and it loses accurate error locations and listings (CW `.lst` format, which hiwave's source view relies on).
2. **Peripheral model:** no existing simulator models the MC9S12DG256 memory map and peripherals, except closed-source SIMHCS12. The GNU sim models the 68HC812A4 (wrong addresses); uCsim appears to be core-only. Peripherals (CRG/PLL/RTI/COP, ECT timer, SCI0/1, SPI, ATD0/1, PWM, ports, flash/EEPROM command state machines, PPAGE banking, interrupt priority via HPRIO) are most of the work anyway, and they must be ours.
3. **Debugger integration:** breakpoints, watchpoints, the cycle counter, "true time" pacing, register and CCR editing, memory change highlighting, stepping by source line vs. instruction, and assembly step over (`BSR`/`JSR`/`CALL`) all need deep hooks. That is easy in-process and painful through GDB/MI against a foreign sim.
4. **Distribution:** shipping cross-built native binaries for Windows, macOS (arm64 and x64) and Linux is a maintenance burden, and GPL code would complicate licensing if the clone is shared.
5. **Performance is fine:** CPU12 bus clock on the Dragon12 is 24 MHz (with PLL; 4/8 MHz without). A well-written TS interpreter (switch dispatch on a `Uint8Array` memory, precomputed opcode tables) should reach tens of MIPS in V8, enough for real-time true-time simulation. This is an estimate (**UNCERTAIN**); benchmark in week 1. Fallback: port the hot loop to Rust/AssemblyScript to WASM with no architectural change.
6. **Scope is bounded:** CPU12 has about 200 mnemonics, about 300 base opcodes plus page-2 (`$18`) opcodes, and indexed postbyte modes (5/9/16-bit offset, auto inc/dec, accumulator offset, indirect). Specs: CPU12RM Rev 4 (covers both HC12 and HCS12 and lists **separate HC12 and HCS12 cycle/access-detail columns**, so use the HCS12 column) [CPU12RM mirror](https://hibp.ecse.rpi.edu/courses/CStudio/hc12/CPU12RM.pdf). Also S12CPUV2 and the MC9S12DG256 Device User Guide plus block guides.

Things to borrow, not ship:
- libasm (Apache-2.0) for encoder cross-checks. Its encoding tables are permissively licensed and could be consulted closely.
- makeprojects (MIT) `.mcp` logic.
- GNU `opcodes/m68hc11-opc.c` and `sim/m68hc11/gencode.c` are GPL. Read them only as reference for flag semantics (DAA, EMACS, MEM/REV/REVW fuzzy instructions, TBL/ETBL, WAV, EDIV/IDIVS edge cases, CCR behavior of LEAx, MOVB/MOVW). Don't copy code into a non-GPL codebase.

Optional hybrid: a "use real CodeWarrior toolchain" setting for students who have CW installed (e.g. invoking `ahc12.exe`/linker via Wine). Not a priority.

## 8. Validation sources (CPU12 test suites, known-good programs)

No public per-instruction CPU12 test vectors exist. Tom Harte-style SingleStepTests/ProcessorTests did not turn up any 6812 set, so that is **UNCERTAIN** but likely absent. Build our own validation from these:

1. **Assembler encoding:**
   - GAS testsuite `gas/testsuite/gas/m68hc11/` (`insns12.s`, `opers12.s`, `indexed12.s` with `.d` expected dumps for 5/9/16-bit indexed offsets, error tests) [dir](https://gnu.googlesource.com/binutils-gdb/+/18287cf8b19533429a4b7f17726c93d1f292e1df/gas/testsuite/gas/m68hc11/).
   - `as -m68hcs12 --generate-example` for every-instruction coverage.
   - libasm `test/reference` and autogen outputs.
   - Diff our encodings against these in CI (convert syntax mechanically for the tests only).
2. **CPU semantics, differential:** random and directed instruction sequences run in our sim vs. the **GNU sim in m68hc12 mode** and/or **ucsim_m68hc12**, comparing A/B/X/Y/SP/PC/CCR/memory. Run the oracles in Docker in CI only. Watch the HC12 vs. HCS12 MOVB/MOVW PC-relative difference.
3. **Ground truth from the real Dragon12** (the student has lab access): D-Bug12's `T` (trace) prints registers after each instruction. A small script can capture golden traces for tricky instructions (DAA, EDIVS, FDIV/IDIV flags, REV/REVW/WAV fuzzy logic, TBL, EMIN/EMAX, BCD, interrupts/RTI stacking order, CCR X/I masking). This is the only authoritative check of flag behavior where docs are ambiguous.
4. **Cycle counts:** CPU12RM HCS12 columns. Generate per-opcode tests automatically from the table.
5. **Whole-program integration:**
   - **D-Bug12 S19 running in the sim.** SIMHCS12 does this, which shows it is a realistic acceptance test exercising SCI, PLL, EEPROM/flash and interrupts.
   - The AN2548 serial monitor source (CW-format asm) assembled by our assembler should be byte-identical to NXP's S19.
   - Dragon12 sample programs: Mazidi *HCS12 Microcontroller and Embedded Systems using Assembly and C with CodeWarrior* (microdigitaled.com "Dragon12 Sample Programs"); Oakland Univ ECE470 asm examples [course](https://www.secs.oakland.edu/~llamocca/Fall2014_ece470.html); Wytec Dragon12 CD examples; NXP AN1456 µC/OS-II-on-Dragon12 sources [element14](https://community.element14.com/products/devtools/technicallibrary/w/documents/11772/an1456-source-code---c-os-ii-and-the-freescale-mc9s12dg256-on-the-wytec-dragon12-plus-evb). Licensing of these is unclear; use them for local testing, not for redistribution.
   - The student's own lab assignments plus CW-generated `.abs.s19` and `.lst` files from the lab PCs are the best end-to-end goldens: assemble the same `.asm` and diff the S19 and listing.

## 9. Proposed module breakdown (all TS)

- `asm/`: lexer → two-pass assembler (CW dialect, macros, conditionals, includes, sections) → object model → absolute linker plus `.prm` subset → S19, listing, map, debug-info JSON.
- `sim/`: `Cpu12` core (table-driven decode, HCS12 cycle table), `Bus` with MMC (PPAGE window `$8000–$BFFF`, register block `$0000–$03FF`, RAM, EEPROM, flash) → peripherals (CRG, ECT, SCI0/1, SPI0, ATD0/1, PWM, ports, IRQ/XIRQ, COP, flash/EEPROM controllers) → `Board` (Dragon12-Plus widgets).
- `debug/`: breakpoint/watchpoint engine, stepping, trace buffer, symbol and line maps. Common interface with back ends `SimTarget`, `DBug12Target`, `SerialMonitorTarget` (AN2548), and later maybe `BdmTarget`.
- `project/`: `.mcp` binary reader, CW XML importer, folder-convention inference, JSON sidecar.
- `ui/`: React + dockview. Panes: Monaco source, assembly/disassembly, register, memory, data/watch, procedure/call stack, command, terminal (xterm), board view. Plus a CW-style project window.

## Key risks / open questions

1. **.mcp for HC12 CW 5.x is unverified.** The makeprojects format notes come from other CW variants. We need 2–3 real `.mcp` files from the lab (plus the XML export if possible) before committing to a parser. The source file list may be recoverable only heuristically.
2. **CW assembler dialect fidelity.** Edge cases (macro parameter syntax, `SET` vs `EQU` scoping, `SECTION` attributes, listing format, error message text, the "absolute" vs "relocatable" assembly wizard templates, `derivative.inc` / `mc9s12dg256.inc` contents) need real CW-generated projects and listings to match. HC12ASMRM is the spec but may differ from actual tool behavior.
3. **No CPU12 golden test vectors exist publicly.** Flag semantics of rare instructions (DAA, fuzzy logic MEM/REV/REVW/WAV, EDIVS overflow, TBL rounding) need hardware traces from the lab board or GPL-oracle differential testing.
4. **HC12 vs HCS12 differences:** cycle counts, PC-relative MOVB/MOVW offsets, and instruction-queue effects. Oracles such as GDB sim may model HC12 rather than HCS12. Use CPU12RM's HCS12 columns.
5. **Peripheral accuracy scope:** ECT, PWM, ATD, SPI, CRG/PLL lock timing, flash/EEPROM command sequences, COP and interrupt priority are large surfaces. Prioritize by what the class uses (likely ports, timer/TOI/OC, RTI, SCI, ATD, PWM, LCD via PORTK, keypad).
6. **Real-board debugging path:** the Dragon12-Plus ships with D-Bug12. CW's "Serial Monitor" target requires the AN2548 monitor in flash, and the source zip's current location is unclear. What does the lab actually use: D-Bug12, Serial Monitor, or P&E BDM? This determines which protocol to implement first. Reflashing the student's board is a support and risk issue.
7. **Break-signal and timing over Web Serial vs `serialport`** for AN2548 attach/reset (**UNCERTAIN**). Prototype early on Windows, where CH340/FTDI drivers vary.
8. **TS interpreter performance** for true-time 24 MHz simulation with peripherals ticking per instruction (**UNCERTAIN**). Benchmark early, and keep a WASM fallback in mind.
9. **SharedArrayBuffer / cross-origin isolation in Electron renderers** for zero-copy memory views (**UNCERTAIN** configuration).
10. **Monaco packaging churn** (ESM and worker changes around 0.53+) in electron-vite production builds. CodeMirror 6 is the fallback.
11. **Licensing:** GPL sources (binutils, gdb sim, uCsim, hcs12mem, USBDM) must stay test-only or reference-only if the clone will be MIT or otherwise permissively shared. NXP-copyrighted files (`mc9s12dg256.inc`, D-Bug12 S19, CW templates) must not be redistributed. Load them from the user's own CW install or lab files.
12. **"As close to actual CodeWarrior as possible":** exact hiwave window behaviors (`.hwl` layouts, command-window command language, `.ini` / `.cmd` startup scripts, the TTS cycle display) are documented only in the TTS/debugger manuals and by observation. Screenshots or recordings from the lab would greatly reduce guesswork.
